## P1
- [x] **[P1] Planned meal servings have no reachable UI at all — view or edit — during normal (unpublished) planning** (meal-plan · mealplan-ui.js:1536,2382,2433-2441 · 2026-09-20)
      Found automating mp-serving (the earlier QA skip's stated reason — "the editable control is in the meal-entry editor dialog" — turned out to be wrong; there is no such dialog). `[data-planned-servings]` is fully wired (querySelectorAll + change handler at line 1536, `updateMealPlannedServings()` at 3299, excluded from drag-start at 2545) and the scaling logic is fully implemented and unit-tested (`meal-plan-servings.js`/`.test.js`) — but **no template anywhere renders an element with that attribute.** The only place `plannedServings` is ever displayed is a read-only `<span class="meal-planned-servings">` (line 2382), and that's inside `mealEntryTemplate`'s `readOnly` branch, gated on `isPublishedMealPlanView(week)` — which can only be true via the backup-restore path, since `toggleMealPlanView` (the only live-UI writer of `mealPlanView="published"`, see the mp-publish entry below) has zero call sites. So during ordinary use, a recipe meal entry's normal (non-readOnly) template (line 2433-2441) shows only the recipe name + a delete button — **no servings display, no servings input, editable or otherwise** — and even the read-only span is itself unreachable outside a restored-from-backup week. The data model, the write path, and the grocery-scaling consumer of `plannedServings` all still work correctly (confirmed: mp-grocery's derivation scales correctly off the recipe's default servings) — only the UI to ever CHANGE it away from the default is gone. Likely the same mealplan-ui.js extraction regression window as mp-publish. Suggested: decide where this belongs in the entry UI (a stepper next to the recipe name in the normal template seems the natural spot) and re-wire `data-planned-servings` there. Verdict: CONFIRMED (dead/unreachable code), not fixed here (out of scope for the QA-fixture task that found it).
      **RESOLVED 2026-09-20:** found the original intended markup intact but unused — a pre-extraction commit (`c57c484`) shipped a `.meal-recipe-plan` wrapper (button + `<label class="meal-planned-servings-editor"><span>Cook</span><input data-planned-servings …><span>servings</span></label>`) in this exact `if (recipe)` branch, and both CSS classes (`.meal-recipe-plan`, `.meal-planned-servings-editor`) were still sitting unused in styles.css — strong evidence this was lost, not redesigned away, during the mealplan-ui.js extraction. Restored that markup verbatim in `mealEntryTemplate` (mealplan-ui.js:2433-2447), gated off (`recipe.virtualGroceryRecipe ? "" : …`) for grocery-item slots, since `updateMealPlannedServings` deliberately no-ops for those (a different, unrelated servings concept) and rendering a visibly-editable-but-inert input there would be a new, self-inflicted bug. Verified live against both the isolated QA fixture and the running dev server: input renders with the recipe's default servings, editing it fires `updateMealPlannedServings`, and the raw `plannedServings` in state actually changes (confirmed via a new `__liveQA.mpPlannedServings()` read-back seam, not just the redisplayed input value) — 2 → 4 in the automated run, 2 → 5 in a manual dev-server check. `qa-p0p1-extended.mjs`'s `mp-serving` item is now a real PASS (was SKIP). Screenshots (desktop full view, desktop close-up, after-change, 360px mobile) confirm no layout regression — the new row fits cleanly under the recipe name in both widths. mp-drag re-verified unaffected (still PASS) since sortable.js's synthetic pointer events dispatch directly on fixed elements rather than hit-testing the point under the cursor, so the entry's added height doesn't change what a pointerdown/pointerup resolves to.
      **SUPERSEDED 2026-09-26 (Luke):** servings should NOT be displayed on meal-plan cards — they're adjusted only inside the recipe view opened from the meal (header `[data-serving-adjuster]` → `updateMealPlannedServingsFromContext`, which writes the entry's `plannedServings`). Card editor + `updateMealPlannedServings` + the read-only span removed; `mp-serving` QA now asserts no servings on the card and drives the recipe-view adjuster (2 → 4 in state, PASS).



## P2
- [ ] **[P2] Finance review-deck swipe hint overlaps its action buttons on short mobile viewports** (finance · styles.css:21748 (`.fin-review-hint`) · 2026-09-20)
      `.fin-review-hint` is `position: absolute; bottom: 14px` regardless of the card's actual content height. Found while screenshotting the review-card/txn-detail unification at 360×740: a review card with enough content above it (e.g. the "N matching transactions" merchant-group banner, or a longer note/category state) pushes the Approve/Edit-details/Skip button row down far enough to visually collide with the "← skip / ↑ ↓ browse / approve →" hint text pinned to the bottom. `pointer-events: none` on the hint means it's not actually blocking clicks, so this is cosmetic, not a functional dead-end — but it reads as broken/cluttered on a real short phone screen. Pre-existing (unrelated to the unification's own changes — confirmed by reasoning through the CSS: the fixed bottom offset doesn't depend on facts-line content). Not fixed here (out of scope for this task); a real fix likely means giving `.fin-review-card-inner` a min-height/scroll accommodation or making the hint row part of normal flow below the actions instead of absolutely positioned. Verdict: CONFIRMED (screenshot in hand), not caused by this session's work.

- [x] **[P2] Meal-plan "publish week" appears to be dead/unreachable code** (meal-plan · mealplan-ui.js:3931 · 2026-09-19)
      `toggleMealPlanView()` — the only function that sets `mealPlanView="published"` from a user action (clones slots, `archivePublishedWeek`, `persistImmediately`) — has **zero call sites** anywhere in the repo: no button, menu item, data-attr, or `addEventListener` binds it, and it's not in the mealplan factory's returned interface. The only other writes of `mealPlanView="published"` are the backup-restore path (`mergeMissingPublishedWeeksFromRestore`). Failure scenario: a user cannot publish a meal-plan week at all (the feature is inert). Likely regression: the trigger was probably dropped during the mealplan-ui.js extraction. Verdict: CONFIRMED (dead code); PLAUSIBLE that it's an unintended regression vs a deliberate removal.
      **RESOLVED 2026-09-20:** Luke confirmed removal (not re-wiring) as the intended fix. Deleted `toggleMealPlanView()` and its exclusive helper `archivePublishedWeek()` from mealplan-ui.js. Left untouched, deliberately: `isPublishedMealPlanView` and the `readOnly` template branches (mealEntryTemplate) — these still serve the backup-restore path (`mergeMissingPublishedWeeksFromRestore`), which can still write `mealPlanView="published"` for a restored week and still needs to render it read-only correctly; and `state.publishedWeeks`/`normalizePublishedWeeks` — an archive of past published weeks, independent of the live-publish action. The QA runner's mp-publish check was removed (not left as a stale SKIP) since there's no longer a publish action for it to exercise. Kept here checked-off for history — see the linked mp-serving P1 finding above, which traces to the same extraction regression window.
